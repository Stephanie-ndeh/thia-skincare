# Story 1.3: Fastify 5 Backend Scaffold

Status: ready-for-dev

## Story

As a developer,
I want the Fastify 5 API server scaffolded with TypeScript, plugin architecture, and core middleware configured,
so that the backend is ready to accept route modules for feature development.

## Acceptance Criteria

1. Fastify 5 project initialized at `apps/backend/` with TypeScript
2. App factory pattern: `app.ts` creates and configures the Fastify instance, `server.ts` starts it
3. Environment variable parsing via Zod in `config/env.ts` (validates all required vars on startup)
4. Supabase client initialized in `config/supabase.ts` using service role key
5. CORS plugin configured to allow only the frontend origin
6. Rate limiting plugin configured: 5/min on `/auth/*`, 100/min on all other routes
7. Global error handler returns consistent JSON error envelope per architecture doc Section 4.3
8. Health check endpoint: `GET /health` returns `{ status: "ok" }`
9. Auth decorator (`authenticate` and `requireAdmin`) implemented per architecture doc Section 4.2
10. `@thia/shared` workspace dependency added
11. `npm run dev` starts the server with hot reload
12. `npm run build` compiles TypeScript to `dist/`

## Dev Notes

- Fastify 5 uses ESM by default — ensure `"type": "module"` in package.json
- `tsx` for development hot-reloading (compiles TypeScript on the fly)
- Supabase service role key bypasses RLS — used for operations like order creation, webhook processing
- The `createSupabaseClient(token)` function creates a per-request client that respects RLS using the user's JWT
- Pino is Fastify's built-in logger — use `pino-pretty` in dev only
- All route modules export a Fastify plugin function: `export default async function(fastify: FastifyInstance) { ... }`
- Do NOT implement route logic yet — just create placeholder files with empty plugin exports
